# T3. 活性と公平性

仕様: `specs/MutexLive.tla` / `MutexLive_NoFair.cfg` / `MutexLive_WF.cfg` / `MutexLive_SF.cfg`

## 1. 安全性だけでは足りない

「何もしない」仕様はあらゆる安全性を満たします。実際に役に立つには
**「待っていればいつかロックが取れる」** という活性が必要です。

```tla
Liveness == \A p \in Procs : (pc[p] = "trying") ~> (pc[p] = "crit")
```

- `[]P`: 常に P。`<>P`: いつか P。
- `P ~> Q`(leads to)= `[](P => <>Q)`: P になったら、いつか必ず Q になる。

## 2. 公平性: 何が「実行されなければならない」のか

`Spec == Init /\ [][Next]_vars` は **何も起きずに止まり続ける** 実行(stuttering)も許します。
だから活性の検査にはそのままでは通りません。「このアクションが実行可能なら、いつか実行される」
という **公平性** を仕様に加える必要があります。

| 公平性 | 記法 | 意味 |
|---|---|---|
| 弱公平性 | `WF_vars(A)` | `A` が **ずっと** 実行可能であり続けるなら、いつか `A` が実行される |
| 強公平性 | `SF_vars(A)` | `A` が **何度も(無限に頻繁に)** 実行可能になるなら、いつか `A` が実行される |

## 3. 3 つの仕様を比べる

```bash
tlc -config MutexLive_NoFair.cfg MutexLive.tla   # 公平性なし
tlc -config MutexLive_WF.cfg     MutexLive.tla   # 弱公平性
tlc -config MutexLive_SF.cfg     MutexLive.tla   # 強公平性
```

| 仕様 | 期待される結果(予想) | 反例の内容 |
|---|---|---|
| `SpecNoFair` | **違反** | 何も起きずに止まる(stuttering)。「プロセスが trying のまま永遠に止まる」 |
| `SpecWF` | **違反** | p2 が「request → enter → leave」を永遠に繰り返し、p1 は trying のまま飢餓(starvation) |
| `SpecSF` | **成功** | 強公平性で飢餓が排除される |

なぜ `WF` では足りないのか: p1 の `Enter` が可能なのは **p2 が lock を手放している一瞬だけ** で、
「ずっと可能」ではありません。だから WF の対象にならず、飢餓が許されます。
`SF` は「何度も可能になる」だけで効くので、飢餓を排除できます。

> [!IMPORTANT]
> **公平性は「環境(スケジューラ)の仮定」** です。`SF` を仮定した検証結果は
> 「スケジューラが強公平なら、飢餓は起きない」という **条件つきの保証** です。
> 実際の OS やロック実装がそれを満たしているか(例: 順番待ちキューを持つか)は別問題で、
> これを仕様に明示的に書かせるのが TLA+ の誠実さです。

## 4. 活性の反例は「ループ」

安全性の反例は有限のトレースですが、活性の反例は **無限に続く実行**(同じ状態に戻るループ)です。
TLC の出力には `Back to state N`(= ループ位置)が付きます。

```
Error: Temporal properties were violated.
State 1: ...
...
State k: ...
Back to state j: <...>
```

「`j` 〜 `k` を永遠に回り続けると、p1 は trying のまま」と読みます。

## 演習

1. `SpecWF` の反例トレースを読んで、「誰が何を繰り返しているか」を自分の言葉で説明する。
2. `SpecSF` から `WF_vars(Leave(p))` を消すと、どうなる? なぜ?
3. プロセスを 1 つにする(`Procs = {p1}`)と、`SpecWF` でも活性が成り立つ。なぜ?
4. 「ロックを待つ人は **FIFO キュー** で順番に入れる」仕様に直して(`queue` 変数を追加)、
   `SpecWF` だけで活性が通ることを確認する。

> [!NOTE]
> <details><summary>ヒント / 解答の方針</summary>
>
> 2. `Leave` がいつまでも実行されない実行が許され、crit に入ったプロセスが居座るので、
>    他のプロセスが trying のまま永遠に待つ。活性違反。
> 3. 競合相手がいないので、`Enter(p1)` は lock が空いている限り **ずっと** 実行可能。
>    WF の「ずっと可能」条件が満たされ、いつか実行される。
> 4. `queue \in Seq(Procs)`。`Request` で末尾に追加、`Enter(p)` は `Head(queue) = p` を条件に追加、
>    実行時に `queue' = Tail(queue)`。FIFO にすると p1 は必ず順番が回ってくるので、
>    `Enter(p1)` は「先頭になった後はずっと可能(lock さえ空けば)」になり WF で十分。
>    **アルゴリズムの工夫で、必要な公平性の仮定が弱くなる**ことがポイント。
>
> </details>

## まとめ

- 安全性 = `INVARIANT`(有限トレースの反例)、活性 = `PROPERTY`(無限ループの反例)。
- 活性には公平性の仮定が必要。`WF` と `SF` の違いを、飢餓の反例で理解する。
- 仮定(公平性)が仕様に明示される = 「どんな環境を前提にした保証か」が見える。
