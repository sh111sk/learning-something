# 01. 形式手法の全体像と 3 ツールの立ち位置

## 形式手法とは

「仕様(あるべき姿)」を曖昧さのない言語で書き、**機械が** その仕様や実装の性質を検査する技術の総称です。
テストは「いくつかの入力で動かして確かめる」ですが、形式手法は
**「入力の全体(または巨大な範囲)について確かめる」** ことを目指します。

## 3 つの軸で見る

### 軸 1: 何を書くか(対象)

| | 書くもの |
|---|---|
| Lean | **プログラムそのもの** と、その性質(定理) |
| TLA+ | **設計** (システムの状態遷移の抽象モデル)。実装コードではない |
| Alloy | **構造** (データの関係・制約)。Alloy 6 では簡単な振る舞いも |

### 軸 2: どう確かめるか(保証の強さ)

```
  強い ←──────────────────────────────────────→ 手軽
  Lean            TLA+ (TLC)            Alloy
  証明            状態の網羅探索          スコープ内の網羅探索
  ∀ 入力          有限モデル               小さい世界
  人間が頑張る     自動                     自動 + 図で反例
```

- **証明(Lean)**: 結論は「すべての n について成り立つ」。ただし証明は自分で書く。
- **モデル検査(TLC)**: 有限に切ったモデル(例: 2 プロセス)の **全ての到達可能状態** を調べる。
  通れば「そのモデルでは確実」、破れれば「バグ + 再現手順(トレース)」。
- **有界検査(Alloy)**: 「要素が各種類 N 個以下」の **全ての世界** を SAT で調べる。
  経験則(小スコープ仮説): 設計の欠陥の大半は小さな反例で見つかる。

### 軸 3: 失敗したとき何が出るか

| | 検証が通らないとき |
|---|---|
| Lean | 「証明が完成していない」(ゴールが残る)。**偽なのか、自分が未熟なのかは分からない** |
| TLA+ | **反例トレース**(初期状態から違反状態までの具体的な手順) |
| Alloy | **反例インスタンス**(違反する具体的な世界の図) |

この差が、日々の使い勝手に最も効きます。

## 「安全性」と「活性」

並行システムの性質は大きく 2 種類です(TLA+ と Alloy 6 のコースで詳しく扱います)。

- **安全性(safety)**: 「悪いことは決して起きない」。例: 2 人が同時に臨界区間に入らない。
  → 反例は **有限のトレース**。
- **活性(liveness)**: 「良いことはいつか必ず起きる」。例: 待っていればいつかロックが取れる。
  → 反例は **無限に続く実行** (同じ状態を回り続ける「ループ」)。公平性の仮定が必要になる。

## 3 ツールの「誕生の背景」

| ツール | 由来 | 立ち位置 |
|---|---|---|
| Lean | 定理証明支援系(型理論)。数学の形式化(Mathlib)とソフトウェア検証の両方で使われる | 「本物の証明」を機械検査する |
| TLA+ | Leslie Lamport。分散システムの設計検証。産業界の設計レビューで使われる | 「実装前に設計のバグを潰す」 |
| Alloy | Daniel Jackson(MIT)。軽量形式手法。ソフトウェア設計のモデリング | 「小さなモデルを書いてすぐ反例を見る」 |

> [!NOTE]
> 「形式証明系が流行っている」背景には、(1) LLM が証明を書く研究・実務(Lean 中心)、
> (2) クラウド事業者での TLA+ 採用など設計検証の実績、(3) 重要ソフトウェアの検証済みコンポーネント化
> があります。「証明」「モデル検査」「有界検査」は競合ではなく **道具箱の別の道具** です。

## このコースの進め方

1. 3 コースで各ツールの「素の使い心地」を体験する(同じ **相互排他** も題材に出てきます)。
2. `compare/` で 4 つの題材を 3 ツールで並べ、**どの題材で誰が楽か** を体感する。
3. 最後に使い分けの判断軸(`compare/README.md`)で整理する。
